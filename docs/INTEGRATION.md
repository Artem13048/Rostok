# План интеграции

## Сейчас

Браузер → ES-модуль core.mjs → ранжирование → приложение app.mjs. Данные: JSON/CSV, localStorage. Никакого серверного execute или автоматических отправок нет. Статический хостинг отдаёт только файлы. Приватный сайт использует режим доступа платформы, не собственную модель ролей.

## Этапы

1. Read-only адаптер товарного/складского учёта: сопоставление идентификаторов, единиц, дат, себестоимости и возвратов. Импорт с dry-run, идемпотентностью и проверкой качества.
2. Адаптер CRM предоставляет только агрегаты сегментов. Имена/телефоны/адресаты остаются в CRM, там же проверяется действующее согласие.
3. Серверный движок сохраняет снимок данных, версии правил и рекомендации с TTL. Локальные правила можно перенести без зависимости от LLM.
4. Prepare создаёт редактируемый черновик с конкретными параметрами. Approve проверяет revision и права фермера. После изменения параметров согласие недействительно.
5. Execute (отдельный адаптер) требует подтверждённую актуальную версию, idempotency key, ограниченные права и проверку политики. Повторная доставка не повторяет внешнее действие. Ошибка не считается выполнением.
6. Записать ответ площадки, аудит и статус; возможность проверить/отменить, где это поддерживается.

## Предлагаемый API, НЕ реализован в текущем MVP

- POST /api/v1/imports: проверка/загрузка обезличенного набора.
- GET /api/v1/recommendations: три действия и их основания.
- POST /api/v1/actions/:id/prepare: конкретный черновик.
- POST /api/v1/actions/:id/approve: farmer_id, revision, approval и expires_at.
- POST /api/v1/actions/:id/execute: серверная проверка подтверждения и идемпотентности.
- GET /api/v1/audit: журнал в рамках владельца/организации.

Объект действия: id, tenant_id, type, product_id/segment_id, snapshot_id, rules_version, score, reason, evidence[], effect{low,high,unit,horizon,assumptions[]}, steps[], revision, status, approval, external_result. Суммы хранятся в копейках; даты UTC, дневные границы явно заданы для хозяйства. Ошибки 400/401/403/409/422/429/503. Контракт утверждается перед реализацией.

## Защита

SSO/OIDC, серверный tenant_id и владение объектом, RBAC, ограничение размера/частоты, HTTPS, KMS/vault для ключей, аудит append-only, срок хранения и удаление, изоляция организаций, SAST/SCA и проверка зависимостей. Эти меры не выдаются за уже реализованные в статическом MVP.

LLM допускается для объяснения и черновиков. Числа вычисляет сервер, LLM не управляет approve/execute. Полученный текст недоверенный, его нельзя исполнять как HTML или команды. Отдельно проверять полноту данных, конфликт действий, сезонность и эффект после пилота.

## Реализованная LLM в версии 1.1

WebLLM 0.2.86, отдельный Web Worker, Qwen 2.5 0.5B и 1.5B. Runtime и WASM с того же origin; веса с фиксированных ревизий Hugging Face. Модель получает ограниченную сводку агрегатов и вопрос, создаёт только текст. Инструментов approve/execute у неё нет. Перед копированием текста предусмотрена ручная проверка; предупреждения отмечают отдельные новые числа, обещания и заявления о выполнении. Это не полная защита от галлюцинаций/prompt injection. Графики, приоритет и прогноз не зависят от LLM и доступны без неё.
